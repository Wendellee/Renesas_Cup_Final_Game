# 15 分钟答辩讲稿

目标时长：14 分 30 秒。整体采用“总—分—总”结构：先说明项目全貌，中间依次展开硬件、软件和关键技术，最后用验证结果和总结收束。

## 00:00–00:45　封面

各位评委老师好，我们的项目是“基于 RA8P1 的光伏板智能巡检系统”。

项目面向光伏板表面巡检场景，将负压吸附、履带移动、端侧识别、无线图传和远程控制集成在同一平台中。

接下来我会先介绍项目全貌和系统总体框图，再分别展开硬件、软件、算法与通信控制，最后汇报验证结果。

## 00:45–01:55　项目概述

这个项目可以概括为一句话：让一台吸附式巡检车完成感知、判断、执行与回传。

应用场景是光伏板表面巡检，设备既要保持附着和移动，又要采集有效图像。系统由 Vehicle 双核巡检车和 RemoteCtrl 触控遥控终端组成。车端完成图像采集、缺陷识别、基础导航和运动执行，遥控端负责触摸交互和实时图像显示。

核心能力包括 Ethos-U55 加速的 YOLO 缺陷检测，以及基于底部 ROI 的连续帧导航判断。架构上坚持实时控制优先：图像和控制消息分流，执行机构由 Cortex-M33 统一管理。

目前两个终端已经形成端到端功能链路。

## 01:55–03:10　系统总体框图

这一页分成上下两层来看。上层是三个设备之间的数据关系，下层是巡检车内部的处理流程。

第一条是控制流：遥控器向检测小车发送动作指令；第二条是图像流：检测小车把实时画面回传到遥控器；第三条是结果流：检测小车将缺陷图上传到上位机。箭头旁的字节数、信道和通信方式是链路参数，不影响主流程的阅读。

下层按照从左到右的顺序，依次是图像采集、缺陷识别、导航与控制、运动执行。图像由 OV5640 采集，M85 和 Ethos-U55 完成视觉处理，M85 给出导航判断，M33 统一控制履带电机和负压风机。

下面就沿着这三条数据流，分别介绍它们由哪些硬件和软件实现。

## 03:10–04:20　硬件总体框图

硬件以 RA8P1 核心板和自研扩展底板为中心。

输入侧包括 OV5640 摄像头、控制接收 nRF24 以及电源和驱动供电。RA8P1 内部，Cortex-M85 处理视觉，Ethos-U55 执行神经网络推理，Cortex-M33 负责实时控制。扩展底板通过 MIPI-CSI、SPI、UART 和 GPT PWM 等接口连接外围模块。

输出侧包括本地 LCD、视频发送 nRF24、DA16200、履带电机和负压风机。页面下方用整机、相机和底板实物图对应框图中的模块。

这张框图回答“硬件如何连接”，下一页继续说明“这些模块在结构上如何安装”。

## 04:20–05:10　硬件三维模型

三维模型页面首先分成“检测小车”和“遥控器”两个独立终端。

选择“检测小车”后，可以先查看小车总体模型，再逐一查看五块已经接入的板卡模型：RA8P1 底板、电机驱动底板、夹芯板 3.0、LCD V3.1 和 OV5640 相机板。每块板都可以单独点击、旋转和缩放。选择“遥控器”后，则进入独立的遥控器模型目录。

讲解时遵循“终端总体—内部模块—装配关系”的顺序。这样既能说明每个终端由哪些硬件构成，也不会把小车端与遥控端的模块混在一起。

## 05:10–06:40　软件总体流程

软件按照 M85、M33 和遥控终端三层展开，每个方框都对应现行线程或明确的数据交接点。答辩时可以点击任意方框，查看该部分的职责、输入、输出和对应代码位置。

M85 侧共有六个任务。Camera Thread 从 OV5640 和 VIN 获取 1024×600 RGB565 帧，并通过“最新帧指针”和直接任务通知交给后续任务。AI Thread 完成 Helium 预处理、U55 推理和 YOLO 后处理；Encode Thread 并行生成 200×112 Gray8 与 JPEG。Display Thread 消费检测结果并叠加检测框，Navigation Thread 读取 Gray8、执行 ROI 状态机并产生动作意图。最后，导航命令以“动作、序号和校验”的 32 位消息发送，JPEG 则通过共享 SDRAM 双槽和描述符交给 M33。

M33 侧共有五个任务。IPC Thread 校验导航消息并消费共享 JPEG；JPEG 元数据分别投递给 Video TX Thread 和 Wi-Fi Upload Thread，前者执行 nRF24 分片发送，后者独占 DA16200 UART/TCP 状态机。导航命令与 Command RX Thread 收到的手动控制包都会覆盖写入单槽“最新命令”邮箱。

Vehicle Thread 是执行机构的唯一所有者。它读取最新命令、检查启动门控和 500 毫秒导航超时，再通过 Vehicle Service 和 GPT 适配层输出左右履带及负压风机 PWM。

遥控端有四个任务。控制方向是“触摸与 GUI 事件—Command TX Thread—8 字节控制包—车端 Command RX”；视频方向是“32 字节图像包—Video RX Thread—分片重组—CRC32—TJpgDec—LCD 显示”。

因此整个软件流程同时明确了任务职责、数据格式、跨核方式和硬件所有权。

## 06:40–08:05　AI 与导航算法流程

在软件总流程基础上，这一页展开 M85 侧的两条视觉路径。

第一条是缺陷识别。M85 使用 Helium 完成图像预处理，Ethos-U55 执行 YOLO 推理，随后由后处理生成检测框和置信度，最终用于显示叠加和检测图快照。

第二条是自动导航。系统把图像转换为 200×112 Gray8，统计底部 24 行中央 ROI，并通过连续帧状态机输出停止、前进和左转意图。状态机包含预热、安全、过渡、转向锁存和恢复状态，避免单帧噪声直接驱动车轮。

两条路径分别回答“识别到了什么”和“车辆下一步怎么运动”。

## 08:05–09:20　通信与控制链路

通信和控制按照数据类型分为四条路径。

遥控指令使用 8 字节控制包、2 Mbps 空中速率、信道 76 和硬件 ACK。无线图传使用信道 100 和 32 字节分片，通过 NO_ACK 冗余与帧级 CRC32 保证坏帧不会进入显示。双核内部的 JPEG 走共享 SDRAM，导航意图走 32 位短 IPC。检测图则由 M33 独占 DA16200 状态机并通过 TCP 上传。

不同来源的控制命令最后统一进入单槽最新命令邮箱，再由 Vehicle Thread 操作执行机构。导航消息超过 500 毫秒不更新时停止车轮。

## 09:20–10:40　关键设计总结

在硬件、软件和算法展开之后，可以把关键设计归纳为四点。

第一，视觉和控制分区。M85 负责高吞吐视觉任务，M33 独占运动控制。

第二，图像所有权可追踪。共享 JPEG 使用双槽和完成通知，消费完成前不能覆盖对应缓冲区。

第三，命令统一收口。手动和自动动作都通过同一邮箱进入 Vehicle Thread。

第四，控制链路超时保护。导航消息中断后不会让旧命令持续驱动车辆。

这些设计共同服务于实时性、可靠性和后续维护。

## 10:40–12:50　验证结果与工程边界

目前已经在目标板上验证双核启动与任务协作、OV5640 图像采集、1024×600 RGB565 显示、200×112 Gray8 JPEG、共享 SDRAM 图像传输、遥控链路、无线图传、Wi-Fi 上传、ROI 自动导航和 500 毫秒失联停车。

Ethos-U55 的 YOLO 预处理、推理、后处理和结果快照链路已经完成软件集成，但模型精度仍需结合赛题数据集验收。

项目仍有明确的工程边界：真实负载下的吸附力、持续电流、温升和运动参数需要整定；FPS、连续帧号和长期丢帧率尚未量化；风机动力链会干扰 MPU6050 的 I2C，因此当前航向闭环关闭。

## 追问准备

### 为什么使用双核，而不是把所有任务放在 M85？

视觉采集、JPEG、AI 和显示具有高吞吐与不确定执行时间；运动控制需要稳定的硬件所有权和超时保护。将执行路径放在 M33，可以在视觉链路短时阻塞时继续保持控制边界。

### 为什么视频链路没有开启 ACK？

视频允许丢弃个别坏帧，但不能让 ACK 重发持续占用空中时间。现行方案对边界包和数据包使用不同冗余次数，并通过帧级 CRC32 验证完整性；控制链路仍保留 ACK。

### 500 ms 是否就是最终安全阈值？

不是。500 ms 是当前软件保护值，后续仍要根据真实速度、制动距离和板面摩擦重新整定。

### 为什么当前关闭 MPU6050？

目标板测试确认风机动力链会触发 I2C 传输中止。为避免不稳定姿态数据进入控制闭环，现行版本暂时隔离 MPU6050，并禁止无承托垂直运行。
